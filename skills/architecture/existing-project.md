# Existing project

1. **Survey, don't read.** From the project root, run `node <this skill's folder>/../../bin/al-dente.js survey`. It numbers the code's folders (with file counts and their most connected files) and lists how many imports go from each folder to each other one, plus folders that import each other. That is the structure: open a source file only when a folder's role isn't clear from its name and files.
2. **Propose 3–8 parts** by grouping the numbered folders by role (screens, app logic, data access, shared helpers, …), and take each part's `uses` from the imports that already exist, so the plan matches the code. Name the imports that go the wrong way (a lower part reaching up, folders importing each other) and ask, in one `AskUserQuestion` call, whether to allow each or keep it as a known break to fix later. Known breaks never block: only new ones do.
3. **Every folder a part imports from must be in a part.** A part importing a file no part claims is a rule break, so put shared helpers and utilities in a part. Entry points, scripts and config files that only import parts may stay outside every part.
4. After the user agrees, write `al-dente.json`, run `node <this skill's folder>/../../bin/al-dente.js check` from the project root, and report the result in a sentence (existing breaks are expected; say they won't block). Then offer the live map.
